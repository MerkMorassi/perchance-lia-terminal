# THE WALL - THE BACKGROUND IMAGE, AND THE TWO PLACES HIS CODE HAD TO CHANGE TO WORK

2026-09-30

## WHAT HE SAID

He pasted the plugin's own shape back at me, with the properties turned into rolls, and no prose at
all:

    background = {import:background-image-plugin}

    bgData
      url = http://i.imgur.com/64c6NnI.jpg
      size = {cover|contain^0.5|auto|{50-500}px^2}
      repeat = {no-repeat|repeat}
      position = center
      opacity = 0.8
      filter = invert({0|100}%) blur({0^3|10}px) hue-rotate({0-100}deg)

In this editor that is the whole instruction: put this in. The turn before it had been the plugin's
docs plus "what do you think?", and my answer offered two roads - the plugin as-is, or a CSS variable
the terminal's own code could drive. He took the plugin road, and handed me the code rather than
arguing for it.

## WHAT WAS BUILT

Three things, and only three, because the plugin needs nothing else:

- `main.pjs` - `background = {import:background-image-plugin}` beside the other four imports, and the
  `bgData` list, with a banner comment carrying the reasoning below.
- `index.html` - `[background(bgData, 0.8)]`, a square block just under the door markup.
- Documentation: THE WALL in `README.md`, §1cm in `TODO.md`, and this entry.

No `src/js` file was touched, no command was added (`commands.json` is still 76), and nothing in the
terminal reads `bgData`: no lane, no mood, no prompt of hers, no archive. The roll happens once per
page load because that is when a square block is evaluated.

## WHAT WAS THOUGHT

**First, read the plugin instead of trusting the docs.** It is 1.3 KB and makes exactly one element:
a `position:fixed` div covering the viewport at `z-index:-1000`, with the image, size, repeat,
position, filter and opacity in its inline style. There is no script in it at all. That mattered,
because the question "will this fight the terminal's own CSS?" is answered by one fact: a negative
z-index FIXED div is visible only where the page is transparent.

**So I measured whether this page is transparent, and it is - which is what makes the wall work.**
`#output` (the main stage), `#upperDeck` and `#progressRail` all compute to `rgba(0,0,0,0)` over the
black body, so the wall is behind the text across the WHOLE page, not tucked into the margins. On a
page of opaque panels this plugin would have been a nearly invisible feature; here it becomes an
actual wall. That is the reason it works, and it is also the reason legibility suddenly became a
question about the picture's brightness rather than a CSS question.

**Two things in his code could not be shipped as written, for opposite reasons - one was simply
broken, and one worked but would have been a ghost.**

- `http://i.imgur.com/64c6NnI.jpg`: an http image on this https page is blocked as MIXED CONTENT. No
  error a person would ever see - just a blank wall, which reads as "the plugin does not work" and
  would have sent us both hunting in the wrong place. Imgur is also deleting old images; the plugin's
  own docs say so in red, and then use Imgur URLs throughout their examples anyway. So I fetched that
  exact picture once (1500x994, 278,247 bytes, byte-for-byte), looked at it, and re-hosted it on
  perchance's upload service. He gets the picture he chose; the wall gets a URL that will still be
  there next year. His own remark - that perchance upload is useful "for other tasks" - is exactly
  this: it is how a picked image becomes a permanent part of a generator.
- `opacity = 0.8`: **the plugin has a bug.** In its `bgData` branch it tests the list's own field but
  emits the FUNCTION ARGUMENT - so `[background(bgData)]` renders the wall at `opacity: 1` and 0.8
  does nothing at all. The plugin's docs advertise `opacity` as a supported property, which is why
  this is worth writing down rather than just patching: the list keeps his 0.8 (read on its own, the
  list should still say what the wall is) and the call site passes it, so the value is in one place
  and takes effect in the other.

**Then I measured the picture, because it is a bright one and the wall sits behind every line of
text.** It is a high-key snow-and-cloud ridge: mean luminance 0.71, with 80% of its pixels above 0.5.
Composited over black at the wall's alpha, and scored against the terminal's `#00ff00` (relative
luminance 0.715 - WCAG wants 4.5:1 for body text):

| roll | mean | median | 10th pct |
| --- | --- | --- | --- |
| `invert(0%)` at 0.8 | **1.58:1** | 1.43:1 | 8.10:1 |
| `invert(100%)` at 0.8 | **4.75:1** | 10.04:1 | 14.38:1 |
| `invert(0%)` at 1.0 (the plugin's own behaviour) | 1.29:1 | 1.17:1 | 7.24:1 |

Two consequences. First, his `opacity = 0.8` is worth a real point of contrast, so the bug above was
not cosmetic. Second, the filter roll splits the site in two: `invert(100%)` produces a dark wall
(composited mean luminance 0.11) that reads the way a terminal wants, while `invert(0%)` puts bright
cloud behind green text and is, over most of the frame, not readable. Both rolls are what he wrote, so
both were left exactly as written - but the numbers are now in the README, so nobody lands on the
bright roll and hunts for a bug that is not there.

**The road not taken, named so it is not forgotten.** The alternative I had offered was a
`--lia-backdrop` custom property in `terminal.css`, driven by the terminal's own code - which would
have let the wall follow her moods, the veil or the vault, and would have cost nothing at runtime
except the bytes. He chose the plugin, and the plugin is what is in. The variable road is still open
and is additive: it needs no change to `bgData`, no new import, and no un-building of this. Recorded
in THE WALL and in §1cm so a future session does not have to re-derive why one was picked over the
other.

## WHAT WENT WRONG

Nothing broke, and the two near-misses are both worth keeping:

- The first thing I did was grep `main.pjs` for the name `background` before adding the import, on the
  theory that a top-level name colliding with an existing list would be a silent disaster. There was
  no collision - but the check is the reason this is a two-line change rather than a debugging
  session.
- The harness lesson from the last session held again, in a new shape: the round of verification that
  reported the wall was done by reading the EMITTED DIV's computed style (`position`, `z-index`,
  `opacity`, `background-image`, the rolled `background-size` and `filter`) and fetching the asset for
  a status code - not by looking at a picture of the page, because the full-page capture helper still
  hangs in this session. The wall's invisibility mode (mixed content) and the opacity bug are both
  things that a screenshot would have shown as "no wall" or "wall too strong", with no way to tell
  which; the computed style told us exactly which value was wrong and why.

## STILL OPEN

- **The bright roll.** `invert(0%)` at 0.8 is 1.58:1 behind green text. Pin the filter, drop the
  alpha, or re-host a baked-dark version of the same picture - all one-line, none taken without his
  word, because the randomization is his.
- **The blur on a phone.** A quarter of loads roll `blur(10px)` on a full-viewport fixed layer, which
  is the expensive kind of filter. Not measured on a low-end device yet. If it janks, bake the blur
  into the file.
- **Per-mood walls.** If the wall should ever change with her moods rather than per page load, that is
  the CSS-variable road above.
- **Nothing is saved.** The import, the list, the call and all of the documentation above are in the
  editor's files; the public page still has no wall until SAVE is pressed.
