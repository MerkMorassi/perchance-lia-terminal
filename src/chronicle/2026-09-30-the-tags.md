# THE TAGS - MALE OR FEMALE, AND ONLY WHERE IT IS KNOWN

2026-09-30 - the VOX panel learned to say which voices are men and which are women, and the pass turned
up a quiet bug that any table-driven feature would have walked into.

## WHAT HE SAID

One sentence, sent with the same breath as a much larger direction:

> *"For the moment, I ask that the available voices be TAGGED - Male or Female - in the VOX system."*

and, around it, the direction itself:

> *"Custom voice and TTS is the goal. Paying ElevenLabs forever is not. I have plenty of captured audio

He also thought he might not have sent the voice he configured for her. He had.

## WHAT WAS THOUGHT

**A TAG MUST BE A CLAIM THE TERMINAL CAN STAND BEHIND.** Two of the four roads publish a sex at all: the
local model's roster carries `gender` for every voice, and the ElevenLabs palette states it in each
voice's own note (an account's list carries it in `labels.gender`). Those tags are the provider's word
and nothing was guessed. The other two roads - this browser's `speechSynthesis` list and the live wire -
expose no such field at all. There the only thing left is the NAME, which is why the table exists, and
why the chip's own title says the tag is **inference** and where to correct it. The house does not
confuse the two, and the panel does not either.

**A MISSING CHIP IS AN ANSWER, NOT A HOLE.** Sixteen of the browser voices are the generic Google
language voices (`Google español`, `Google 日本語`, ...) - no name to read - and fourteen of the thirty
wire voices are named after STARS, which no official listing sexes. They were left blank rather than
guessed, because a wrong tag is worse than an empty one, and because a blank that means "not known" is
honest in a way that a confident guess is not. The panel says so in words, so a reader can tell an
unanswered voice from a forgotten one.

**AND ONE NAME THAT MUST NOT BE IN THE TABLE.** `River` is **female** in the local model (`af_river`)
and ***neutral*** at ElevenLabs. One name key could only hold one answer and would lie about the other,
so the name is deliberately absent: each road's own word states it, and the table is asked only when
nothing else answers. It is a small example of the general rule - the table is a last resort, not the
first.

## WHAT WENT WRONG

**`design()` is a WHITELIST, and a new block is invisible until it is named there.** The tagging was
written, the table was correct, the styles were right - and every browser and wire row still showed no
chip, while the regex path worked perfectly. The cause was one level up: `voice.defaults()`, which
`design()` returns, does not hand back the whole `voices.json` - it names each field it carries
(`engine`, `limits`, `elevenlabs`, `kokoro`, `roles`, ...), so the brand-new `sex` block never reached
`sexMap()` and the table was always `{}`. Measuring it (by printing what `sexOf` returned for known
names, and by fetching the served JSON to prove the file itself was right) found it in a few minutes.
The fix is one line - `sex: (cfg && cfg.sex) || null` in `defaults()` - and the lesson is worth as much
as the feature: **a whitelist accessor silently swallows every field it was not told about**, so a new
block in a design file is not "added" until it is added there too.

## WHAT ELSE HAPPENED - THE ORIGIN MOVED (and it was not the code)

Halfway through this pass the generator was **renamed**, and the live page said so in three fields at
once: `window.generatorName` went `2hoy6c5u0x` -> **`mythos-lia-barbelo`**, `window.generatorPublicId`
went `60a6e23d...` -> **`7f77c07f...`**, and `location.origin` moved to the new subdomain with it
(`window.generatorIsUnsaved` also went to false - it is saved now). Browser storage is keyed to the
subdomain, so on the new origin the terminal is empty: kv `lia_settings` holds only `folders` and `sync`
(no `voice`, no `story`, no `agent`, no keyring), and the vault measures **0 records, 0 bytes** where the
previous session measured 189. The old name no longer exists
(`getGeneratorStats?name=2hoy6c5u0x` -> `generator-does-not-exist`), while the new one carries the
generator and its `$meta` intact - so this was a rename, not a fork, and the ID moved with the NAME.

**The house had this written down and believed the opposite.** `src/TODO.md` said *"A RENAME is also free
- the name is the path, the ID is the origin"*; the measurement says the ID is **not** stable across a
rename, which is what the platform's own note means by *"renaming it changes the subdomain ... unless
they rename back to the old name."* Both the old claim and its correction are now in the file, because a
wrong belief that is left standing is worse than one that was never written.

Nothing in this pass caused it, nothing in this pass can undo it, and **the agent renamed nothing** - it
observed, it wrote the finding down, and it flagged it. The record is not deleted: it is on the other
subdomain, and the name is the key to it.
